# Changelog

## 2.0.12
- Fixed a P2 finding from the same external analysis: `wrapCellValues()` ran unconditionally for every enhanced table, wrapping every `td[data-label]`'s content in `<span class="rwd-value">` regardless of whether that table would ever actually stack into cards, and regardless of the "Fill data-label" setting. Confirmed the risk was real, not theoretical: this mutation can break a template's or third-party script's own selectors (`td > a`, `td > img:first-child`, `td:empty`) and changes `childNodes` for anyone else reading the cell — including on tables that live comfortably at desktop width and never stack at all.
- `wrapCellValues()` now only runs lazily, from inside `observeWidth()`'s `apply()`, on a pass where the table is actually about to be (or already is) `.is-stacked` — a table that never crosses the breakpoint never has its cells touched. `wrapCellValues()` was already idempotent per cell (`data-rwd-wrapped` guard), so calling it on every already-stacked pass afterwards remains a safe no-op.
- Verified via headless render: a table in a 900px wrapper (never stacks) ends with zero `span.rwd-value` elements and its `<a>` cell content remains a direct child of `<td>` (`td > a` still matches); a table in a 300px wrapper (stacks) is wrapped as before; and a table that starts wide and is then resized narrow gets wrapped at exactly the point it crosses the breakpoint, not before. All prior fixes (2.0.2–2.0.11) re-verified unaffected by this change.

## 2.0.11
- Fixed a P2 finding from the same external analysis: `ensureWrap()` assumed `table.parentElement` was never `null` and called `parent.insertBefore(...)` unconditionally — a detached table (built in memory by another script, or momentarily disconnected during a DOM move) would throw a `TypeError` there and abort the whole `forEach` in `enhance()`, leaving every table after it in that pass unprocessed.
- `ensureWrap()` now returns the table itself when it has no parent, instead of throwing.
- Honest note on reachability: `collectTables()` only ever finds tables via `document.querySelectorAll()`, which by definition only returns elements currently connected to the document — so within the plugin's own code as written today, a table reaching `ensureWrap()` with `parentElement === null` in the same synchronous pass doesn't appear to occur. The guard is still worth having: it's a one-line, zero-downside protection against API misuse or a future refactor (e.g. a `MutationObserver` path that processes `addedNodes` directly instead of re-querying the document) reintroducing exactly this crash.
- Verified against the real, exported `enhance()` (via `window.rwdTablesEnhance()`), not a reimplementation: `document.querySelectorAll` was temporarily wrapped to also return a genuinely detached `<table class="responsiv">` (created but never appended anywhere) alongside the page's real table. The call completed without throwing, the detached table was processed without error (no wrap, since there's nowhere to put one), and — the actual point of the fix — the real table on the page was still fully processed (`data-rwd-ready`, wrapped) rather than the whole pass aborting on the bad one.

## 2.0.10
- Fixed a P2 finding from the same external analysis: `observeWidth()`'s `ResizeObserver` (and the `window.addEventListener("resize", apply)` fallback for browsers without it) never disconnected/removed themselves — on a page that dynamically swaps tables in and out (an editor, an AJAX-refreshed panel, notably more likely now that 2.0.9 added opt-in DOM watching), that's a growing memory leak and pointless callback work for elements no longer on the page.
- `apply()` now checks `target.isConnected` on each run and tears itself down at that point (`ro.disconnect()` for the `ResizeObserver` path, `window.removeEventListener` for the fallback) — opportunistic rather than instant (neither mechanism itself reports removal), but correct, and simpler than adding a second observer just to watch for removals in what should be a rare case. `WeakRef` was considered and left out: the actual retention is `ResizeObserver`'s own internal tracking and the `window`-level listener closure, not something a `WeakRef` on our side would change — disconnecting explicitly is the real fix.
- Verified via headless render on the fallback path (forced by deleting `window.ResizeObserver` before the script loads, since it's the deterministically testable one — the `ResizeObserver` fires only on genuine size changes, not on disconnection alone, so it can't be triggered on demand the same way): `removeEventListener('resize', ...)` fires exactly once after the table is removed and a resize occurs, and a further resize afterwards produces no additional add/remove calls, confirming the listener is genuinely gone rather than silently re-added.

## 2.0.9
- Added an opt-in "Watch for dynamically added tables" setting (default off), addressing a real gap the same external analysis pointed out: `enhance()` only ever ran once (DOMContentLoaded) plus whenever a page explicitly calls `window.rwdTablesEnhance()` — a table injected later by AJAX (a lazy-loaded tab/accordion panel, SP Page Builder, a custom fetch) stayed unprocessed unless whoever built that integration happened to know about the manual escape hatch.
- This is a genuine trade-off, not a plain bug fix: an always-on `MutationObserver` watching the whole page would be exactly the kind of standing cost a system plugin running on every request shouldn't impose by default, which is what an earlier review pass in this same project explicitly (and correctly) argued against. Making it an opt-in setting, off by default, resolves that tension — sites that need it can turn it on, sites that don't pay nothing extra.
- When enabled, a `MutationObserver` on `document.body` looks for added `<table>` elements (or any added node containing one) and re-runs `enhance()` via `requestIdleCallback` (or `setTimeout` where unsupported) — safe to call repeatedly since `data-rwd-ready` already makes it a no-op for tables already processed.
- Verified via headless render: with the setting off, a table injected 100ms after page load stays unprocessed (matches prior behaviour exactly); with it on, the same injected table is automatically enhanced (`data-rwd-ready="1"`, wrapped) with no manual call needed.

## 2.0.8
- Fixed a P2 finding from the same external analysis: `ensureWrap()` recycled an existing `.table-wrapper` div unconditionally — a template that wraps a whole block of content in one `.table-wrapper` containing two (or more) tables meant both tables shared a single wrap. Confirmed: two tables in one `.table-wrapper` measured `tables: 2` on the same element. Consequences: `observeWidth()` ran twice on that one element (two `ResizeObserver`s, two `scroll` listeners on the same node), `.is-stacked` was driven by the shared wrapper's width rather than either table's own situation, and a `.no-responsiv` table inside it would still get the shared wrap's classes.
- `ensureWrap()` now only reuses an existing `.table-wrapper` when it contains exactly one `<table>`; otherwise the table gets its own `.rwd-table-wrap` nested inside it, same as any table with no pre-existing wrapper.
- Added a `data-rwd-observed` guard in `observeWidth()` so the same target element can never end up with a second `ResizeObserver`/scroll listener, as defense in depth beyond the `ensureWrap()` fix.
- Verified via headless render: two tables in one shared `.table-wrapper` now each get their own independent wrap (`data-rwd-observed="1"` on both, confirmed as two distinct elements) and the shared wrapper itself is left untouched (no `rwd-table-wrap` class); a single table in a `.table-wrapper` still recycles it exactly as before (no regression).

## 2.0.7
- Addressed another P2 finding from the same external analysis: the scrollable wrap gained `tabindex="0"` (since 1.2.0/2.0.6) but no `role="region"` and no accessible name — a screen reader would announce the Tab stop with nothing to identify it by. Added `role="region"` plus `aria-label`, sourced from the table's own `<caption>` when present, otherwise a translated fallback string.
- Non-trivial architecture note the analysis caught: plugin language files install under `administrator/language` regardless of client (Joomla's `PluginAdapter`/`Installer::parseLanguages()` always uses client id 1 for plugins), and `$autoloadLanguage` was removed in 2.0.0 as apparently-unused — so the frontend had no plugin strings loaded at all. Fixed by calling `$this->loadLanguage()` explicitly in `onBeforeCompileHead()` before resolving `Text::_('PLG_SYSTEM_FGRESPONSIVETABLES_SCROLL_REGION')`, then handing that string to JS via `addScriptOptions` (`scrollLabel`) — `Text::_()` alone on the frontend would have silently returned the raw, untranslated key.
- Verified via headless render across three cases: a scrollable table with a `<caption>` (label taken from the caption, ignoring `scrollLabel`), a scrollable table with no caption (label falls back to the translated `scrollLabel`), and a table that isn't scrollable at all (no `tabindex`, no `role`, no `aria-label` — confirms the "only when needed" behavior from 1.9.5/2.0.x still holds).

## 2.0.6
- Addressed a P2 finding from the same external analysis: the horizontal-scroll shadow/keyboard-focus feature (1.2.0/1.2 era) was effectively dead code in practice. `table.responsiv { width: 100% }` with `table-layout:auto` and no `min-width` means a browser will shrink columns to fit rather than overflow, so in the width band between the stacking breakpoint (default 600px) and "plenty of room" — a tablet, a narrow module, an open accordion — a wide table neither stacks into cards nor scrolls; it just squeezes into unreadable multi-line column headers, and `scrollWidth` never exceeds `clientWidth` so the scroll cue and `tabindex` never activate. Confirmed: a 700px wrapper with five long headers measured `clientWidth === scrollWidth === 700`.
- Added a new setting, "Minimum table width (px)" (default 0 = off, matching prior behaviour exactly). When set, JS sets a `--rwd-min-width` custom property (inline style) on the table's wrap, and CSS applies it as `min-width` on the non-stacked table — giving the browser a genuine reason to overflow instead of shrink, which is what the existing scroll-shadow/`tabindex` logic actually needs to have anything to react to.
- Verified via headless render, same scenario both with the setting off and on: off is byte-for-byte the old behaviour (`scrollWidth === clientWidth`, no `tabindex`, no scroll shadow); on with e.g. 900px measures `scrollWidth` 900 vs. `clientWidth` 700, `tabindex="0"` is added, and `can-scroll-right` activates — the existing (already well-written) scroll indicator now has a real signal to respond to.

## 2.0.5
- Fixed the fourth real bug from the same external analysis, and the sharpest one: `applyLabels()` tracked column position with a fresh `colIndex` per row, so a `<td rowspan="2">` in one body row silently shifted every later cell in the FOLLOWING row one column to the left (nothing there to advance past). Confirmed before the fix: `<tr><td rowspan="2">Pondelok</td><td>AD08</td><td>60 €</td></tr><tr><td>AD20</td><td>70 €</td></tr>` labelled the second row's cells "Deň"/"Stroj" instead of "Stroj"/"Cena" — a real price shown under the wrong column name on mobile, not just misalignment.
- `applyLabels()` now tracks an `occupied` grid across rows (`"row:col" -> true`), the same approach `headerLabels()` already used for header rows with rowspan/colspan — a rowspan cell reserves its column in the following row(s), so the next row's real cells correctly advance past it instead of shifting into its place.
- Verified via headless render on the exact reported scenario: the second row's cells now report `data-label="Stroj"` and `data-label="Cena"` (previously "Deň"/"Stroj"). All fixes from 2.0.2–2.0.4 re-verified unaffected (colspan/rowspan header resolution, tbody th row-header, no-thead fallback header row).

## 2.0.4
- Fixed a third real bug from the same external analysis: a table with no real `<thead>` — the common TinyMCE output where the author types `<tr><th>...</th></tr>` as the first row directly inside `<tbody>` — had its header row correctly read by `headerLabels()`'s existing fallback, but nothing hid that row visually in stacked mode, so it rendered as its own near-empty card of bare `<th>` cells side by side. A quieter second bug in the same case: `applyAriaRoles()` decided "is this a header cell" purely from `row.parentElement === table.tHead`, so those `<th>` cells got `role="rowheader"`/`scope="row"` (a row header) instead of the column-header role they actually are — wrong structure for screen reader users.
- Added `markHeaderRow()`: when a table has no `table.tHead` and its first row's cells are all `<th>`, tags that row with class `rwd-headrow`. CSS hides it the same visually-hidden way as a real `<thead>`, and `applyAriaRoles()`'s `inHead` check now also recognizes it, so those cells get `role="columnheader"`/`scope="col"` correctly. Runs unconditionally (not gated behind the "Fill data-label" setting), since the visual-hiding half of the fix matters regardless of that setting.
- Verified via headless render: the marked row is visually hidden (position:absolute + zero-size clip, same as thead), its `<th>` cells report `role="columnheader"`/`scope="col"`, `data-label` on the following data row is unaffected, and the card list shows exactly one card per data row with no extra near-empty header card. Fixes from 2.0.2 and 2.0.3 re-verified unaffected.

## 2.0.3
- Fixed another real bug from the same external analysis: a `<th scope="row">` used as the first cell of a body row (a common accessible "row header" pattern, instead of a plain `<td>`) was never switched out of `display: table-cell` for the stacked layout — it rendered as a narrow strip taking only its own content width inside a now-block `<tr>`, with empty space beside it, instead of spanning the card like every other line. Confirmed via computed style (`display: table-cell`, ~60px wide) and screenshot before the fix.
- `tbody th` / `tfoot th` now get `display: block`, styled as the card's header line (reusing `--rwd-head`, matching the visually-hidden `thead`'s own header color).
- First attempt at the fix used `width: 100%` alongside padding, which overflowed the card by ~19px (no `box-sizing: border-box` is set anywhere in this stylesheet) — removed the redundant `width: 100%` instead, since a block-level element already fills its container's width correctly on its own; a border-box reset for the whole plugin was considered but not applied, to avoid touching unrelated layout that has never needed it.
- Verified via headless render: `display` is now `block`, width matches the card (322px vs. 324px card width, the 2px being the card's own border), and the row-header line visually spans the full card as its header, both before/after screenshots compared. Existing long-value-wrap and rwd-nowrap behavior from 2.0.2 unaffected.

## 2.0.2
- Fixed a real card-overflow bug found by an external analysis (Perplexity): the mobile card's value column used `white-space: nowrap` with a plain `auto` grid track, so a long text value (a note, a description — not just a short price) forced the whole card wider than its wrap and overflowed sideways with no visual cue (the scroll-shadow indicator and keyboard focus are both intentionally suppressed while `.is-stacked`, since a stacked card shouldn't normally need to scroll at all). Measured at 360px viewport before the fix: wrap `clientWidth` 344px vs. `scrollWidth` 834px.
- Value now wraps by default (`white-space: normal; overflow-wrap: anywhere;`), and both grid columns use `minmax(0, ...)` so the tracks can actually shrink below their content's natural width — the earlier plain `1fr auto` looked fine for short values only because grid's default track minimum is content-based, not because the layout was actually safe. Added an opt-in `rwd-nowrap` class for a `<td>` whose value is always short and should never wrap regardless of the label next to it.
- Verified via headless-browser render: the reported scenario now measures `scrollWidth === clientWidth` (344px), long values wrap and stay inside the card, short values are unaffected, and `rwd-nowrap` still forces a single line when explicitly requested.
